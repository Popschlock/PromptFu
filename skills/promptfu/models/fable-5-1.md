# Profile: Claude Fable 5.1 / Mythos 5.1

Last verified 2026-09-05 against the official "Prompting Claude Fable 5.1" guide and the "What's new in Claude Fable 5.1" release notes. Re-verify on point releases.

**Layered profile — read `fable-5.md` first.** Anthropic's guidance is that Fable 5 prompts run on Fable 5.1 without changes, so everything in `fable-5.md` applies in full: intent + constraints instead of procedures, delete Opus-era scaffolding, never request reasoning echo, the four classifier categories and the defensive reframe, evidence-grounded progress, maker-never-grader. This file holds only what 5.1 changed and what it newly wants.

## Where Fable 5.1 fits

- **Successor to Fable 5 at the same input/output price** ($10/$50 per MTok) with **cache reads at a quarter of the cost** ($0.25 vs $1 per MTok). Long agentic sessions that re-read a cached prefix got cheaper, so compact later than you did on Fable 5.
- **Anthropic's own routing:** start on Opus 5 for most workloads; pick Fable 5.1 for demanding reasoning and long-horizon agentic work, or when Opus 5 at higher effort still falls short on your evals. That is SKILL.md's Opus-default / Fable-on-exceptions rule, with "genuinely long-horizon" now an up-front trigger rather than only "Opus stalled". Whenever an exception fires, Fable 5.1 is the target — Fable 5 is legacy.
- **A new cost route.** At `low`, Fable 5.1 is often competitive on cost per task with Opus and Sonnet at higher effort while scoring higher; `medium` roughly matches Fable 5 at lower cost. Where you would run Sonnet 5 `xhigh` or Opus 5 `high`, Fable 5.1 `low`/`medium` is a candidate — evals decide, and the effort floor still applies (surface it as a recommendation, never apply it silently).
- **Published gains concentrate in:** agentic coding over hours-long sessions (multi-file features, refactors, migrations, cross-session review); documents, spreadsheets and slides from a blank page; multistep research; vision on dense charts and tables nested in PDFs; reasoning across the full 1M window; computer use with recovery from failed steps. Multilingual on par with Fable 5.
- **Mythos 5.1** is the same model for Project Glasswing participants only; it does not run the prefix-binding check described under API notes.

## Core shift vs Fable 5

Fable 5.1 does **more on its own and says less while doing it**. Seven default behaviors moved, each fixed by one prompt line and none by restructuring: fewer user-facing updates during long tool runs (more so at higher effort); one tool call per turn in agent loops where the next reads are only implied; denser prose; less formatting in chat; unmarked quotations in summaries; whole-file rewrites for small edits; answering from memory at `low`. And on open-ended feature work it delivers what was asked *and more* — nearby fixes, unrequested extensions, extra committed tests — unless told what to leave out. The prompting job is the same shape Opus 5's turned out to be: constrain, don't scaffold.

## Delete on sight (habits from Fable 5 and earlier that now misfire)

- **Narration suppressors** ("hold all findings for the final response") — 5.1 is already quiet; these make it silent for minutes. Remove them before adding anything.
- **Anti-formatting rules** written for bullet-happy earlier models ("never use bullets or bold") — 5.1 under-formats already; replace with a rule that says *when* formatting is appropriate (see Always add).
- **Compile-check phrasing** ("Does this program compile without errors?") — a known safeguard false-positive trigger; ask "Are there any bugs in this program?"
- **Effort levels carried over from Fable 5** — the names do not map to the same amount of thinking; re-run the sweep. And a long deliverable requested at `xhigh`/`max` gets drafted in thinking and then written again in the reply.
- **Forced tool use** (`tool_choice` of `any` or `tool`) in any dispatch that builds raw calls — it is a 400 on 5.1. Say in the prompt when the tool applies instead; explicit tool instructions are followed reliably.

## Refusal / safety hazards

Same four `stop_details` categories as Fable 5 (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`); all of `fable-5.md` → Safeguards holds, including routing genuinely security/bio/competing-model work to Opus 5 up front. Fewer false positives than Fable 5 had at launch, and **finding vulnerabilities in source code is permitted**. Three 5.1-specific triggers:

- **Compile-check phrasing** (above).
- **Lesser-known programming languages** — give context on what the language is and how it works, or hand the model the language's documentation.
- **Base64 in tool output** — tools that return base64-encoded data into context trip the classifier; strip or remove them.

Permitted fallback targets are Opus 4.8 and Opus 5 (`fallbacks: "default"`, beta, retries on Anthropic's recommended model per category). A refusal that arrives before any output is not billed; fallback credit refunds the prompt-cache cost of switching.

## Always add (the 5.1 deltas — same content set as every target, only the form differs)

Everything in `fable-5.md` → Always add still goes in. On top of it, 5.1 wants the following, each a short line or block rather than a procedure:

- **Narration contract, for human-in-the-loop work.** Say when you want text and what each update holds: "Before you start, say in a line what you're about to do; brief updates while you work help the user follow along. Close with a short recap that stands on its own — what you found, what you did, and what's next — so a reader who only sees the last message has the full picture." Skip it for unattended dispatch, where quiet is fine. If the UI hides tool output, say so ("Only you see that command's output — if the user needs to read any of it, put it in your reply") or the model runs commands to "show" the user things they never see.
- **Batching nudge in agent loops** where the next reads are implied rather than named (custom coding agents, bash-and-editor harnesses, computer use): "First privately list what you need next; then request every item that doesn't depend on another's result in this one response." No effect on answer quality; saves a round trip per read. Carry it as a turn-scoped system message if the harness supports the beta (API notes), else a text block after the tool results.
- **Finish-the-task pair, for autonomous runs.** Apply both; the first alone keeps most of the effect, and its opening sentence carries it — keep that sentence as written. (1) "You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking 'Want me to…?' or 'Shall I…?' will block the work. For reversible actions that follow from the original request, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Offering follow-ups after the task is done is fine; asking permission before doing the work is not." Add the assessment exception (when the user is describing a problem or thinking out loud, the deliverable is the assessment — report and stop) and the last-paragraph check ("if it is a plan, a question, or a promise about work you have not done, do that work now with tool calls; end your turn only when the task is complete or you are blocked on input only the user can provide"). (2) The delivering-work block: the request, or the plan the user approved, sets the scope and the scope is the deliverable — don't quietly narrow, widen or swap it; make routine judgment calls, check in only when readings would lead to materially different work; do everything that doesn't depend on an open question first; if one part is blocked, complete every other part and say exactly what was left out; a step you have decided on is something to run, not to announce. Trade-off: this pair also makes the model less likely to ask about genuinely ambiguous requests. If the product needs specific confirmations, list them right after the opening sentence.
- **Scope-and-tests limiter, for feature work:** "If, while working or testing, you find a pre-existing bug, a performance concern, or behavior the task doesn't mention, don't fix, optimize or extend it in this change unless the requested behavior cannot work without it; report it as a follow-up in your summary. Where the task is ambiguous, implement the reading its wording and the surrounding code most directly support, state that assumption in your summary, and don't build for the other readings as well. Verify your work however you like; scratch scripts and quick checks need not be kept. Commit tests only where the task asks for them or this repository already keeps tests for this kind of change, sized like the neighboring test files — roughly one focused test per stated behavior — and don't turn scratch checks into additional permanent test files. This is about extras only: implement every behavior the task asks for, completely." Measured: unrequested additions and committed test code drop substantially with no change in task success.
- **Prose density.** "Please remove all mannered prose." usually works; the long form defines the anti-pattern (metaphor and flourish standing in for direct statement — "a dial worth turning" for "a parameter worth varying"; say what you mean, use the literal phrase when one exists). Put it in the user message by preference.
- **A formatting rule that says when:** "Use lists and bullet points when asked to, or when the content is multifaceted enough that they help with clarity. If the person explicitly requests minimal formatting, always format your responses without bullet points, headers, lists, or bold emphasis, as requested. In conversational, personal, or emotional exchanges, keep to plain prose."
- **Targeted-edit line, for file-editing agents:** "The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing." Brings small and medium edits back in line with Fable 5.
- **One complete worked example, for summarizing retrieved sources:** the user's request, the response, and one sentence on why it is correct — organized around where sources agree and differ, each source conveyed in the assistant's own indirect speech, at most a short marked phrase quoted. The example fixes the unmarked-quotation drift where a rule does not. Write the templated tool lines with your tool's real name so they read as tool output, not text to emit.
- **Search nudge at `low`:** "When a query centers on a name you do not confidently recognize, or recognize from a fast-moving area like AI models and developer tools where the landscape shifts within months, the name itself is the thing to verify: search before answering, and include the name as the user wrote it in at least one query alongside any reformulations. Partial background is exactly what makes an out-of-date answer sound authoritative, so familiarity is not a reason to skip the search." Or raise effort for just those turns (per-message effort, API notes).
- **Long-deliverable note at `xhigh`/`max`,** appended to the user message with the real value filled in: everything produced in one reply, reasoning and drafting included, counts toward a single limit of about [max_tokens] tokens; composing the deliverable in full as reasoning and again as the reply doubles the turn without improving it; spend the reasoning space on understanding the request, checking inputs and settling structure, and the output space on writing. Cuts thinking sharply on prose and code requests.

## Dispatch settings (subagents/loops)

- **Effort:** default `high`. Sweep `low|medium|high|xhigh|max` on 5.1's own evals — level names do not carry over from Fable 5. Gains over Fable 5 are largest at higher settings; `medium` ≈ Fable 5 for less; `low` is a real tier now (often beats Opus/Sonnet at higher effort on cost per task). Run long-deliverable requests at `high` unless a measured gain justifies `xhigh`/`max`, and then set `max_tokens` for thinking plus reply and append the long-output note. `low` calls search less — add the nudge or raise effort for those turns. None of the dispatch rules in `fable-5.md` change.
- **Per-message effort** (beta header `mid-conversation-output-config-2026-07-01`) changes effort mid-conversation without invalidating the prompt cache: raise it for the hard step, lower it for routine ones, raise it for a turn that needs fresh search. Prefer this over holding one level for a whole session.
- **Subagents:** let the lead keep working while subagents run — the start tool returns immediately, each result arrives in a later user message, a separate tool waits when the lead chooses to. Lowers average time to completion at similar quality, tokens and cost; the model still often chooses to wait. Maker-never-grader is unchanged.
- **Compaction:** if you compact on the client, replace the whole history with one summary message plus the new user turn and replay nothing else (no thinking blocks carry over, so nothing fails). Tell the summarizer what to keep — the six-item list: difficulties and how they were handled; options raised, tried or set aside and why; anything asked, decided, ruled out or established as a constraint, stated exactly; where things stand; what is still open or promised; hard-to-reconstruct details (names, numbers, dates, exact wording, links) kept exactly — with the user's words kept close and the model's own reasoning condensed. Cache reads are a quarter of Fable 5's price, so compact later than you used to.
- **Progress visibility:** the model's between-tool-call updates come back as `thinking` blocks and are *empty* under the default `thinking.display: "omitted"`. Set `display: "updates"` (beta header `thinking-display-updates-2026-08-18`) and render non-empty thinking blocks as status lines before concluding the model has gone quiet.
- **Vision:** give it crop-and-zoom. A cropping tool that returns an enlarged region delivers most of the uplift; a container with the raw images and PIL/OpenCV gives the rest.

## API notes (if constructing raw calls)

- **IDs:** `claude-fable-5-1`, `claude-mythos-5-1` (Bedrock `anthropic.claude-fable-5-1`; Claude Platform on AWS, Google Cloud and Microsoft Foundry `claude-fable-5-1`). 1M context, default and maximum, standard pricing across the window; 128k max output. Tokenizer unchanged from Fable 5 (~30% more tokens than pre-Opus-4.7 models). 30-day data retention; no zero-data-retention unless expressly authorized.
- **Pricing:** $10 base input / $12.50 5-minute cache write / $20 1-hour cache write / $0.25 cache read / $50 output per MTok; batch $5/$25. Cache reads are 0.025× base input (0.1× on other Claude models). 512-token minimum cacheable prompt.
- **Three breaking changes vs Fable 5:**
  1. `tool_choice: {"type": "any"}` or `{"type": "tool", ...}` → 400 `invalid_request_error` (thinking is always on and a forced call would skip it). Keep `auto` and use `strict: true` or structured outputs for schema-valid JSON; name the tool in the prompt to make it call one.
  2. **Earlier models can't read 5.1 thinking blocks.** A router or fallback that moves the conversation to Opus drops them silently (not billed; reported in a top-level `input_transformations` array with beta header `thinking-binding-controls-2026-08-01`). 5.1 reads earlier models' blocks fine.
  3. **Conversation history must be append-only.** Editing, reordering or removing an earlier turn; injecting a per-turn reminder into an earlier turn and removing it next request; rebuilding `system` or `tools` between requests; or an image/document URL that serves different bytes — each invalidates every later thinking block. Where enforced (accounts created on or after 2026-08-31; older accounts only when `thinking.block_binding.prefix_mismatch_behavior` is set) the next request fails with a 400 `The block is bound to a different conversation`; `prefix_mismatch_behavior: "drop_block"` drops the block and continues (reason `prefix_binding_mismatch` in `input_transformations`). Safe: removing a leading run of thinking blocks oldest-first, server-side compaction or context editing, moving `cache_control` markers, changing `effort`. To audit a harness, run a session with `drop_block` and log `input_transformations`, or confirm consecutive requests are byte-identical up to the appended turns.
- **Turn-scoped system messages** (beta header `mid-conversation-system-clear-at-2026-08-21`): `{"role": "system", "clear_at": "next_user_message", "content": "..."}` inside `messages` carries system-prompt authority for the current turn and stops rendering once a later user message exists. The right carrier for per-turn nudges (batching, "the user can't see that output"): append a fresh copy each turn and leave earlier copies in place byte-for-byte — they cost no input tokens once cleared, and deleting them is a history edit. Without the beta, put the line in a text block after the `tool_result` blocks in the same user message.
- **Unchanged from Fable 5:** adaptive thinking always on (`{"type": "enabled"}` with `budget_tokens`, and `{"type": "disabled"}`, both → 400; omit `thinking` or send `{"type": "adaptive"}`); `thinking.display` defaults `"omitted"`, `"summarized"` available, raw chain of thought never returned; interleaved thinking automatic, no beta header; prefills → 400; non-default `temperature`/`top_p`/`top_k` → 400; mid-conversation system messages and tool changes supported.
- **Refusals:** HTTP 200 with `stop_reason: "refusal"` and a `stop_details` object naming the category; never read `content[0]` unconditionally. Fallback targets Opus 4.8 and Opus 5 (server-side `fallbacks: "default"`, SDK middleware, or your own retry).
- **Provenance:** every text output carries Anthropic's statistical watermark (no tokens or hidden characters added); image/video/audio files retrieved through the Files API carry signed C2PA credentials.
